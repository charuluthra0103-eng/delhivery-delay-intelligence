# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone for the AI & ML Certification Program (E&ICT Academy, IIT Roorkee). The data is synthetic (produced by `generate_data.py`); Delhivery is only the setting. One repository, one branch (`main`), three questions answered in one connected pipeline: how long will a parcel take (Part B), which parcels will miss their promise (Part C), and which hubs need which playbook (Part D). Money is in Indian Rupees (INR).

## How to run

From a fresh clone, in this order:

```
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

`requirements.txt` pins the versions used (pandas 3.0.2, numpy 2.4.4, scikit-learn 1.8.0, joblib 1.5.3). `models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt`, so if your installed versions differ, re-run `package_model.py` instead of loading the committed pickle. Running `predict_delay.py` twice gives byte-identical `outputs/new_shipment_actions.csv`.

Layout: `src/shipment_prep.py` holds `PROMISED_HOURS`, `FEATURES`, `NOISE_COLUMNS`, `clean_shipments` and `build_features`, used by Part A, `package_model.py` and `predict_delay.py` (no second copy of the cleaning logic).

## Data findings

Source files: `outputs/part_a_checks.csv`, `part_a_delay_by_group.csv`, `part_a_correlations.csv`. The export had 1,224 rows; 24 exact duplicates were removed, leaving 1,200 (all survive the hub merge), 278 of them delayed (delay rate 0.2317). Five weight values of 999.0 were scanner-fault sentinels and were treated as missing. The service_type column had 12 spellings before cleaning and 3 after.

1. **Service type.** Express is delayed most often: 119 of 243 parcels, a delay rate of 0.4897 (Standard 0.2056, Economy 0.0857). Express has the tightest promise (36 h) against a mean of 36.8056 h.
2. **Hub tier.** Delay rate rises sharply with tier: 0.0400 (Tier 1), 0.2150 (Tier 2), 0.4400 (Tier 3).
3. **Distance.** Delay rate climbs steeply: 0.0219 (0-200 km), 0.1368 (201-400), 0.4364 (401-600), 0.8523 (601+; 75 of 88 parcels).
4. **Correlations with delivery_hours (top three by absolute value):** promised_hours 0.8372, distance_km 0.4013, n_stops 0.3247. (Next: hub_daily_capacity -0.3237, hub_tier 0.3175.)
5. **Log transform.** declared_value_inr (median-filled) is right-skewed: mean INR 1,533.05 versus median INR 1,121.50 (a gap of about INR 411.55), whereas after the natural log the mean is 7.0277 and the median 7.0224, almost identical, so the log makes the column roughly symmetric and stops a few expensive parcels dominating linear models.

One delivery_hours value falls outside the 1.5 x IQR fences (-0.7063 to 116.5238); it was kept since it is a plausible slow parcel.

## Model results (regression)

Source files: `part_b_*.csv`. Split 840 / 180 / 180. The scaler was fitted on training rows only: the scaled training columns have a largest absolute mean of about 4e-16, while the scaled test rows have 0.2187, proving nothing leaked from test.

- **Baseline.** Predicting the training mean gives validation R2 = -0.0212 (RMSE 18.8552 h): it explains none of the variation, and is the floor any model must beat.
- **Validation winner.** Linear regression, RMSE 4.8912 h (MAE 3.9222, R2 0.9313). Gradient boosting is practically tied (RMSE 4.9165, R2 0.9306), then random forest (5.5095, 0.9128) and the decision tree (6.2796, 0.8867).
- **Tree depth.** Best depth is 6 (val_rmse 6.2796). Depths 1, 2 and 3 are high-bias: both errors are high (depth 1: train 11.6334, val 12.1324, gap only 0.4990; val RMSE 5.85 h worse than the best). Depth 12 and no limit are high-variance: unlimited has train_rmse 0.0 against val_rmse 7.8368, a gap of 7.8368 h (depth 12 gap about 6.0 h); depth 8 is starting to overfit (3.3360 vs 6.7901).
- **Learning rate.** Validation R2 is 0.7127 at 0.01, 0.9306 at 0.1 and 0.8440 at 1.0. 0.1 is best. 0.01 is too slow: 100 tiny steps never get close to the target (underfits, RMSE 10.0018). 1.0 overshoots: each tree overcorrects, so the fit is noisy (RMSE 7.3701).
- **Cross-validation (5-fold, shared KFold object, 1,020 rows).** Linear regression 0.9261 (std 0.0048) and gradient boosting 0.9353 (std 0.0045). The ranking disagrees with the single validation split. Following the brief's rule the final model is the lowest-validation-RMSE candidate, linear regression, scored once on the test rows: RMSE 4.5235 h, R2 0.9493. For production I would nevertheless prefer **gradient boosting**: the CV estimate uses five folds and every one of the 1,020 rows, so it is more reliable than one 180-row split where the two models differ by only 0.03 h; the 0.0092 R2 gain is about two standard deviations; and the data contains interactions (sale x Express, rain x long distance) that a linear model cannot represent.

## Model results (classification)

Source files: `part_c_*.csv`. Stratified split 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

- **Blind baseline.** Predicting "not delayed" for everything gives validation accuracy 0.7667 (TN 138, FN 42, TP 0): it looks decent but catches zero delayed parcels (recall 0), so it is useless for the operations goal. Trained models reach accuracy 0.8833-0.9056 and validation F1: logistic regression 0.8046, decision tree depth 6 0.7470, default forest 0.7848.
- **Noise columns.** The five bookkeeping columns hold a combined 0.2245 of the 17-column forest's importance, even though they carry no signal (forests spread splits over them). By F-score all five fall outside the top 7 (ranks 8, 12, 14, 16, 17; the largest noise F-score is 4.5847, while the smallest F-score in the top seven is 36.7281). The top seven are distance_km, hub_tier, hub_daily_capacity, n_stops, promised_hours, rain_flag, sale_event_flag.
- **SelectKBest k table (validation F1).** k=5 0.6988, k=7 0.8333, k=10 0.7857, k=12 0.8049, k=17 0.7848. Too few features (5) drops real signal; from 7 upward extra columns add only noise. k=7 matches the signal count, so I used it.
- **Tuning.** Grid search (135 fits, best CV accuracy 0.8952) and randomized search (45 fits, 0.8905) gave validation F1 0.7750 and 0.7848, below the untuned forest on the same 7 columns (0.8333). Tuning did not beat the default. With 42 delayed validation parcels, a single changed prediction moves F1 by about 0.02, so differences of this size are noise; a 180-row validation set cannot rank these configurations reliably. By the tie-break rule the final configuration is the default forest (n_estimators 100, no depth limit, min_samples_leaf 1) on k=7 features.
- **Threshold.** Validation table: at 0.5, precision 0.7955 and recall 0.8333; at 0.6, precision rises to 0.8889 but recall falls to 0.7619, below the 0.80 target. The highest threshold with recall of at least 0.80 is therefore **0.5**. Lower thresholds buy recall at the price of many more false alarms (at 0.3: recall 0.9286 but precision 0.6964).
- **Test (once, threshold 0.5).** TN 125, FP 14, FN 10, TP 31: precision 0.6889, recall 0.7561, F1 0.7209, accuracy 0.8667. Test recall (0.7561, 31 of 41) is below validation recall (0.8333, 35 of 42), and below the 0.80 target. The threshold was tuned on validation so validation looks optimistic, and with 41 delayed parcels one parcel moves recall by about 0.024, so the gap of about three parcels is within plausible sampling variation. I report it as is and did not re-tune.

## Operations recommendation

Source files: `hub_profile.csv`, `hub_segments.csv`, `segment_profile.csv`, `part_d_separation.csv`, `tier_vs_segment_mismatch.csv`, `part_c_final_test.csv`, `new_shipment_actions.csv`.

| Segment | Hubs | Mean hours | Delay rate | Mean km | Mean stops |
|---|---|---|---|---|---|
| Standard | 7 | 47.2396 | 0.0257 | 188.9296 | 55.3686 |
| Watch | 8 | 56.8137 | 0.1550 | 314.1762 | 70.7175 |
| Escalate | 9 | 64.6504 | 0.4600 | 470.4757 | 84.3444 |

- **Escalate hubs (delay rate):** HUB13 Nagpur 0.46, HUB15 Kochi 0.36, HUB17 Patna 0.46, HUB18 Ranchi 0.38, HUB19 Guwahati 0.62, HUB20 Raipur 0.48, HUB21 Bhubaneswar 0.40, HUB23 Siliguri 0.44, HUB24 Agartala 0.54. The segment's mean delay rate is 0.46 versus 0.0257 for Standard.
- **Tier labels that mislead (`tier_vs_segment_mismatch.csv`).** HUB07 Kolkata is labelled Tier 1 but behaves like Watch (delay rate 0.14, 304.7 km). HUB13 Nagpur and HUB15 Kochi are labelled Tier 2 but behave like Escalate (0.46 and 0.36). HUB22 Dehradun is labelled Tier 3 but behaves like Watch (0.20). So the tier label should be treated as a static planning attribute, not as a playbook: assign the playbook by the segment, which is recomputed from observed behaviour, and review the four labels.
- **Alert threshold and precision/recall.** The alert threshold is 0.5. On the test rows (`part_c_final_test.csv`), precision is 0.6889, i.e. about 7 of every 10 flagged parcels are really delayed, and recall is 0.7561, i.e. about 8 of every 10 delayed parcels are caught.
- **New parcels.** Of the 48 new parcels, 8 are flagged; 6 of them sit in Escalate hubs and need a hub-manager escalation (the other 2 get a proactive customer call). The remaining 40 need no action.
- **Why K = 3.** The across-to-within ratio is 2.8940 (K=2), 5.3928 (K=3), 6.3047 (K=4) and 6.8866 (K=5), so it keeps rising, as it mechanically must when clusters get smaller. But K=4 (sizes 8-7-5-4) and K=5 (8-7-4-3-2) contain clusters of fewer than 6 hubs, too small to carry their own playbook, while K=3 (9-8-7) gives balanced groups and is the number of playbooks operations runs. The big jump is from K=2 to K=3 (+2.50) and the later gains are small (+0.91, +0.58).

## Production plan

**(a) Production-readiness characteristics mapped to the repository**

- *Accuracy:* validation/test metrics in `part_b_metrics.csv`, `part_c_final_test.csv`; threshold chosen to meet a recall target.
- *Reliability:* `clean_shipments` handles gaps, sentinel weights and spelling variation, and `predict_delay.py` has no missing values in 17 features after `build_features` using stored medians (`models/impute_values.csv`).
- *Reproducibility:* fixed `random_state` everywhere, pinned `requirements.txt`, generated data committed, run order in this README, byte-identical scoring output.
- *Performance (speed):* the final model is a 100-tree forest on 7 selected features; scoring 48 parcels is near instant.
- *Maintainability:* shared logic in `src/shipment_prep.py`, one script per part, the model rebuilt by `package_model.py` from `part_c_final_config.csv`.
- *Consistency:* the same `clean_shipments`/`build_features` functions serve training and scoring, and `models/feature_order.csv` fixes the column order.
- *Monitorability:* outputs are plain CSVs with a probability, flag and action per parcel, enabling the weekly checks below.

**(b) Quantities to monitor, with triggers**

1. Weekly delayed share of delivered parcels. The historical share is 0.2317; investigate if it leaves 0.15-0.31 for two consecutive weeks.
2. Weekly share of parcels flagged. On validation the model flagged 44 of 180 (about 0.24) at the 0.5 threshold; investigate if the weekly share leaves 0.15-0.35 for two consecutive weeks.
3. Recall on parcels whose outcome is now known, measured over a rolling four weeks with at least 40 delayed parcels. Test recall was 0.7561; trigger a review if it drops below 0.60 (the lowest recall I would accept).
4. Input drift: weekly mean distance_km (historical about 315 km median) and mean n_stops; trigger if either moves by more than 10 percent from the training value.

**(c) Retraining and the sale window.** Retrain monthly on the latest outcomes, and immediately if a trigger above fires, repeating the full Part C process and re-running `package_model.py`. The 15-28 September sale window (`sale_event_flag`) lifts hours (by about 7 h, and 12 h more for Express) so a high delay rate during the sale is expected; compare the monitored quantities with the previous sale window (or the same kind of event), never with ordinary weeks, otherwise it will cause false alarms and then hide real problems. Data drift here would look like a change in the distribution of distance, stops or service mix (for example more Express parcels or longer lanes), new hubs, a change in the way rain or sale flags are recorded, or hubs moving between segments in the refreshed hub profile.

## Limitations

1. The data is synthetic, generated from a known formula with Gaussian noise; real delays have richer causes (strikes, vehicle failure) and the very high scores (R2 about 0.93-0.95) would not carry over.
2. The test set has only 41 delayed parcels, so test precision/recall are imprecise (one parcel is about 0.024 of recall), and test recall (0.7561) came in below validation recall (0.8333).
3. The 0.5 threshold and the final configuration were chosen on one 180-row validation split with 42 delayed parcels; the three tuned/untuned candidates differ by only a few predictions and a different split could pick differently.
4. Hub segments rest on 50 parcels per hub and 24 hubs; K-Means results for K=4 and K=5 depend on seed and hub order, and the segments will shift with new data.
5. The model is trained on parcels that were already delivered; delays are measured only against the promise and not against cost, so the real cost trade-off between a call and a missed delay was never quantified.
6. The environment uses pandas 3.0.2 and scikit-learn 1.8.0; the pickle loads only on matching versions, so re-run `package_model.py` on other versions.
